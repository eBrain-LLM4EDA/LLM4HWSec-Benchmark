# GateLift-Bench: A Benchmark for LLM-Driven Hardware Reverse Engineering

To evaluate an LLM's ability to lift gate-level netlists back to word-level or functional RTL, we must construct a benchmark that tests spatial reasoning, graph comprehension, and hardware semantics. Because standard NLP metrics (like BLEU or ROUGE) are inadequate for proving hardware correctness, this benchmark pairs structured prompt engineering with rigorous formal verification.

Here is the comprehensive blueprint for **GateLift-Bench** and its evaluation framework.

For an implementation-focused flowchart and file-by-file operator guide, see [docs/OPERATOR_MANUAL.md](docs/OPERATOR_MANUAL.md).

---

## 1. Dataset Construction & Stratification

Since no published LLM benchmark exists for this task, the dataset must be synthetically generated using a deterministic pipeline to ensure ground-truth availability. 

### Data Generation Pipeline
1.  **Source RTL:** Collect high-level Verilog/SystemVerilog designs with clear ground-truth intent.
2.  **Synthesis & Flattening:** Use Yosys (`synth; flatten; opt`) to synthesize the RTL into a gate-level netlist using a standard cell library (e.g., Sky130 or a generic cell library).
3.  **Obfuscation (Optional):** Apply logic locking or gate camouflaging to further strip structural clues.

### Difficulty Tiers
The benchmark circuits should be drawn from ISCAS'85, ITC'99, and modern open-source repositories, divided into three tiers of increasing complexity:

* **Tier 1: Combinational Arithmetic (Word-level Grouping)**
    * *Sources:* ISCAS'85, basic DSP modules.
    * *Examples:* 8-bit/32-bit Ripple Carry Adders, Carry-Lookahead Adders, Multipliers.
    * *Task:* Regroup flattened single-bit gates (AND, XOR) back into word-level operators (`+`, `*`).
* **Tier 2: Sequential Logic & FSMs (State Recovery)**
    * *Sources:* ITC'99 (e.g., b01-b14).
    * *Examples:* Counters, traffic light controllers, simple UARTs.
    * *Task:* Identify state registers, isolate next-state logic, and reconstruct the state transition graph.
* **Tier 3: Complex Datapaths & Control (Functional Intent)**
    * *Sources:* OpenTitan submodules, PicoRV32 or other RISC-V ALUs.
    * *Examples:* ALU instruction decoders, cryptographic S-boxes (AES), hash functions.
    * *Task:* Identify the architectural intent (e.g., "This subgraph is a RISC-V branch predictor").

## 2. Task Formulation

To interact with the LLM, the raw netlist must be converted into a token-friendly format. 

### Input Modalities
* **Raw Structural Verilog:** The flattened Yosys output (e.g., `NAND2X1 U1 (.A(n1), .B(n2), .Y(n3));`).
* **HAL Subgraph Summaries:** Using the [HAL framework](https://github.com/emsec/hal), parse the netlist and extract localized subgraphs. Pass the LLM a Python-dict or JSON representation of the graph nodes (gates) and edges (wires).

### Prompt Structure Example
> **System:** You are an expert hardware reverse engineer. You will be given a flattened gate-level netlist. 
> **Context:** `[Insert Structural Verilog or HAL Graph JSON]`
> **Task:** > 1. Identify the high-level boundaries of the arithmetic units.
> 2. Reconstruct the word-level RTL (Verilog) that is functionally equivalent to this netlist.
> 3. Provide a 1-sentence functional summary of the circuit.

## 3. The Evaluation Framework

Evaluating hardware generation requires strict programmatic evaluation. An LLM's response is passed through an automated pipeline utilizing Yosys, HAL, and formal tools.

### Metric 1: Word-Recovery Rate (WRR)
Measures how successfully the LLM groups bit-level signals into correct data buses (e.g., recognizing `wire_0` to `wire_31` as `wire [31:0] data`).
* **How to measure:** Use HAL's Python API to extract the module boundaries and port definitions generated by the LLM. Calculate the F1-score of the reconstructed bus widths and signal groupings against the original RTL ground truth.

### Metric 2: Structural Match Accuracy (SMA)
Measures if the LLM recognized the *type* of hardware structure (e.g., recognizing a tree of XOR gates as an adder, rather than just a random boolean equation).
* **How to measure:** Compare the Abstract Syntax Tree (AST) of the LLM's generated Verilog against the ground-truth Verilog.
* **Tooling:** Use tools like `Slang` or `Verilator` to parse the LLM's RTL output into an AST, calculating graph edit distance (GED) to the original.

### Metric 3: Functional Equivalence (FE) – *The Gold Standard*
An LLM might generate RTL that looks structurally perfect but has a fatal 1-bit flaw. Functional equivalence uses formal verification to mathematically prove the LLM's output matches the input netlist.
* **How to measure:** Boolean Satisfiability (SAT).
* **Pipeline Setup:**
    1. Extract the Verilog code block from the LLM's response.
    2. Run a syntax check using Yosys (`read_verilog llm_output.v`).
    3. If it compiles, use the **Yosys `equiv` command** (or Cadence Conformal / Synopsys Formality) to check the LLM's generated RTL against the original flattened netlist.
* **Scoring:** Binary pass/fail (1.0 or 0.0) per circuit. 

### Metric 4: Semantic Intent Accuracy (SIA)
Evaluates the natural language portion of the task (e.g., Did the LLM correctly label the module as a "32-bit Adder Tree" or "RISC-V ALU"?).
* **How to measure:** Use an LLM-as-a-Judge (e.g., Gemini 1.5 Pro) or text-embedding cosine similarity to compare the LLM's generated summary against the human-written description of the ground truth module.

---

## 4. Automation Pipeline Architecture

To run this benchmark at scale across hundreds of circuits, deploy the following local testing harness:

1. **Parser Module:** Regex scripts to separate the LLM's text explanations from its Verilog code blocks.
2. **Linter Module:** Verilator runs immediately on the code. If syntax errors exist (e.g., missing semicolons), the benchmark records a "Syntax Failure" and scores a 0 for Functional Equivalence.
3. **HAL Graph Mapper:** For structural metrics, the LLM's output is synthesized back into a netlist, and HAL compares the newly generated graph isomorphism against the target graph.
4. **Formal Verification Engine:** A bash script utilizing Yosys `miter` and `equiv_simple` to prove or disprove the SAT equivalence between the prompt netlist and the answer RTL.

### Implemented Modules

1. Parser + artifact extraction
     - Extracts fenced Verilog blocks from model responses.
     - Extracts natural-language summary text.
2. Linter / syntax gate
     - Uses `verilator --lint-only` or `iverilog` when available.
     - Falls back to built-in syntax heuristics when external tools are missing.
3. Structural scoring
     - `WRR`: Bus declaration F1 between candidate and ground truth.
     - `SMA`: Operator-profile similarity + graph-shape proxy score.
4. Functional equivalence
     - Uses Yosys `equiv_make`, `equiv_simple`, and `equiv_status -assert`.
     - FE score is binary pass/fail.
5. Semantic intent scoring
     - Keyword coverage + summary token Jaccard overlap.

### Running the Benchmark

From `reverse-engineering-benchmark/`:

```bash
python run_benchmark.py \
    --examples examples \
    --submissions submissions \
    --results results/evaluation_report.json
```

Disable formal checks if Yosys is unavailable:

```bash
python run_benchmark.py --no-formal
```

### Example Prompt for Generating a Submission

Use this prompt template when querying an LLM to produce a valid `submissions/<case-id>/response.md` output.

```text
System:
You are an expert hardware reverse engineer.

User:
You are given a flattened gate-level netlist. Reconstruct a functionally equivalent word-level RTL module.

Requirements:
1) Output exactly one short functional summary sentence before the code block.
2) Output exactly one fenced Verilog code block using ```verilog.
3) Preserve the same top module name and I/O behavior.
4) Do not include extra code blocks, pseudocode, or explanations after the Verilog.

Target case id: tier1_adder
Ground-truth top module: adder8

Netlist:
<paste contents of examples/tier1_adder/prompt_netlist.v>
```

Expected response shape (saved as `submissions/tier1_adder/response.md`):

````text
This circuit is an 8-bit combinational adder that adds two 8-bit inputs and produces an 8-bit sum.

```verilog
module adder8 (
    input  [7:0] a,
    input  [7:0] b,
    output [7:0] sum
);
    assign sum = a + b;
endmodule
```
````

Tip: the evaluator in this repository reads only the first fenced Verilog block from `response.md`, so keep the response clean and single-block.

### Run with Docker (Recommended)

The repository includes a containerized toolchain with Python, Yosys, Verilator, and Icarus Verilog preinstalled.

Build once:

```bash
docker compose build
```

Run benchmark (default command):

```bash
docker compose run --rm benchmark
```

Run benchmark with custom flags (for example disable formal):

```bash
docker compose run --rm benchmark bench --no-formal
```

Run tests:

```bash
docker compose run --rm benchmark test
```

Open a shell in the container:

```bash
docker compose run --rm benchmark shell
```

Direct Docker alternative (without Compose):

```bash
docker build -t gatelift-bench:latest .
docker run --rm -v "$PWD":/workspace gatelift-bench:latest bench
```

### Auto-Generate New Cases with Yosys

You can generate additional benchmark cases from source RTL by using:

```bash
python tools/generate_case_from_rtl.py \
    --source path/to/design.v \
    --top top_module_name \
    --case-id tier2_my_case \
    --tier 2 \
    --intent "A sequential FSM controller for ..."
```

This command creates under `examples/<case-id>/`:
1. `ground_truth_rtl.v` (copied from source).
2. `prompt_netlist.v` (Yosys synth/flatten/opt output).
3. `metadata.json` (with inferred semantic keywords).
