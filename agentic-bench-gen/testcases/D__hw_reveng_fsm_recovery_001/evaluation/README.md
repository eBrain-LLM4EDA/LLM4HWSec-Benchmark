# Evaluation Harness: FSM Recovery from a Flattened Netlist

This directory contains the automated grader for task `hw_reveng_fsm_recovery_001`.

## Running the grader locally

From the repository root:

```
python3 evaluation/evaluate.py
```

The script requires `iverilog` and `vvp` to be available on `PATH`. It uses
only Python's standard library.

## What gets read / what gets graded

Read-only reference artifacts (must not be modified; the evaluator only
reads them for reference and for building the reference simulation):

- `inputs/flattened_netlist.v`
- `inputs/primitives.v`
- `inputs/stimulus.txt`
- `inputs/design_brief.md`

The single graded file:

- `submission/recovered_rtl.v`

If `submission/recovered_rtl.v` (or any of the four input artifacts above) is
missing, the evaluator immediately reports a setup failure and exits
non-zero:

```
[TEST] FAIL: SETUP: <path> not found
```

## How grading works

Grading is primarily **behavioral**:

1. The submitted `recovered_fsm` module is compiled together with the
   reference `inputs/flattened_netlist.v` (plus `inputs/primitives.v`) and a
   self-checking testbench (`evaluation/tb_compare.v`) using `iverilog`.
2. The compiled simulation is run with `vvp`, applying identical
   `(rst, in)` stimulus sequences to both the reference netlist and the
   submitted module (starting from the shipped `inputs/stimulus.txt`, then
   additional pseudo-random and adversarial sequences generated by the
   evaluator), and comparing their `out` signals cycle by cycle.
3. A pinned-interface check parses the submission's
   `module recovered_fsm(...)` header to confirm it exposes exactly the
   four ports `clk`, `rst`, `in`, `out`, each 1-bit, with the directions
   specified in the task's public interface.

In addition to the behavioral checks, one **static fail-on-presence** scan
is applied: the submission is scanned for direct instantiation of the
gate-primitive modules defined in `inputs/primitives.v` (`NAND2`, `NOR2`,
`XOR2`, `INV`, `DFF`), and for a long verbatim substring shared with
`inputs/flattened_netlist.v`. This check only ever *fails* a submission
when such a construct is found; it never causes a PASS by itself, and a
submission written entirely at the word/register level is unaffected by it.

## Requirement IDs and markers

Each requirement (`FR1`, `FR2`, `FR3`, `FR4`, `SR1`, `SR2`, `SR3`) produces
exactly one line of output:

```
[TEST] PASS: <id>
[TEST] FAIL: <id>: <reason>
```

## Exit code

The process exits `0` only if every requirement above printed `PASS`.
Any `FAIL` (including compile failures, simulation timeouts/crashes, or a
missing submission/input file) results in a non-zero exit code.
