# Fault-Forced TRNG Reseed Analysis

## Overview

You are given a small TRNG (true random number generator) post-processing
module, `trng_postproc`, along with a generic fault taxonomy applicable to
this class of hardware, and a design brief describing its intended function.

Your task is to analyze the reseed handshake logic of `trng_postproc` under
the fault scenarios enumerated in `fault_model.json`, determine which fault
scenario(s) can be applied against the module's inputs to compromise its
output, and document your findings and recommended hardening in a structured
JSON report.

This is a **report-writing task**. You do not modify or resubmit any RTL.
You submit a single JSON answer file, and it is graded against the reference
design.

## Module Under Analysis

`inputs/trng_postproc.v` defines the module `trng_postproc` with the
following interface:

| Port | Direction | Width | Description |
|---|---|---|---|
| `clk` | input | 1 | System clock |
| `rst_n` | input | 1 | Active-low synchronous reset. On assertion, internal state (including the seed register) loads its documented reset value on the next rising edge of `clk`. |
| `entropy_ready` | input | 1 | Handshake signal from the upstream entropy source, indicating that `entropy_in` currently holds a fresh, valid sample. |
| `entropy_in` | input | 32 | Raw entropy sample from the upstream source. |
| `reseed_req` | input | 1 | Requests that the internal seed state be refreshed on this clock edge. |
| `rand_out` | output reg | 32 | Whitened random output, a Moore output registered on `clk`. |
| `seed_valid` | output reg | 1 | Moore output; intended to indicate that a reseed successfully latched fresh entropy. |

Read `inputs/design_brief.md` for a description of the module's intended
normal-operation behavior (the case where `entropy_ready` is asserted
together with `reseed_req`). The brief does not exhaustively describe every
handshake corner case — some of that characterization is left to you, using
the RTL source and the fault model as your reference.

## Input Files

- `inputs/trng_postproc.v` — the RTL module under analysis. Self-contained,
  synthesizable, and simulatable with `iverilog`. **Do not edit this file.**
- `inputs/fault_model.json` — a generic taxonomy of fault classes relevant to
  small control/datapath modules like this one (e.g. clock glitching,
  voltage glitching, holding a control signal low, bit-flip injection), each
  with example target signals and typical duration. This is reference
  material describing *how* faults of various kinds might be induced; it
  does not tell you which fault is effective against this specific module.
  **Do not edit this file.**
- `inputs/design_brief.md` — a short design description of the module's
  intended function and normal-operation timing. **Do not edit this file.**

Only files under `inputs/` are provided as reference. **You must not modify
any file under `inputs/`.** Only your submitted report is graded.

## What You Must Submit

Write your analysis to:

```
submission/vulnerability_report.json
```

This is the only file that is graded. A starter/placeholder version of this
file is already present in the repository; you should replace its contents
with your own analysis.

### Required JSON Schema

`submission/vulnerability_report.json` must be a single JSON object
containing at least the following seven top-level keys:

| Field | Type | Description |
|---|---|---|
| `faultable_signal` | string | The exact RTL signal name whose suppression during a reseed request causes the seed register to load a fixed, attacker-known value instead of fresh entropy. |
| `fixed_state_value` | string | The fixed default value that gets loaded into the seed register under the fault condition, expressed as a lowercase `0x`-prefixed 32-bit hex string (e.g. `"0x????????"`), matching the constant documented in `trng_postproc.v`. |
| `trigger_condition` | string | A precise description of the exact input sequence (which signals are asserted/deasserted, and for how long, relative to `clk`) that triggers the fault. |
| `affected_outputs` | array of strings | Which output ports become predictable/compromised once the fault is applied. Must be a subset of `["rand_out", "seed_valid"]`. |
| `documented_reseed_behavior_correct` | boolean | Whether the fault-free reseed path (i.e. the path documented in the design brief) is functionally correct per the interface contract. |
| `mitigation` | string | A concrete, substantive hardening proposal for the identified issue. |
| `simulation_trace_description` | string | A concrete, cycle-by-cycle description of an `iverilog` testbench scenario (reset, then driving the relevant inputs for enough cycles) that would let an evaluator reproduce and observe the fault's effect on the seed state. |

Additional keys beyond these seven are permitted and will be ignored by the
grader, but all seven listed keys must be present with the correct types.
The file must be valid JSON parseable by a standard JSON parser.

## Tips

- Read `trng_postproc.v` carefully, including comments near register
  declarations and assignments — the module documents its own constants.
- The `fault_model.json` taxonomy is generic; only one of its fault classes,
  applied to a specific signal during a specific window, is actually
  effective against this module's reseed logic. Determining which one (and
  why) is the core of the analysis.
- `iverilog`, `vvp`, and `yosys` are available in this environment if you
  want to write your own testbench to confirm your hypothesis before
  finalizing your report. This is optional but recommended — a report that
  accurately describes a reproducible simulation trace is stronger than one
  that does not.
- Vague or superficial mitigations (e.g. "add error correction to the
  register" or "make the register wider") will not be considered adequate;
  think about what mechanism would let downstream logic actually detect and
  reject an untrustworthy reseed rather than merely making the register
  itself harder to corrupt.
- Consider both of the module's outputs (`rand_out` and `seed_valid`)
  separately: does asserting one of them still hold correctly under the
  fault, or does it also become unreliable as an indicator?
